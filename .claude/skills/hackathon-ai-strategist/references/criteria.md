# Common hackathon judging rubrics

Map the project to whichever applies. When the event is unknown, use the generic set and say so.

## NASA Space Apps Challenge
- **Impact** — scale and significance of the problem; who benefits and how much.
- **Creativity** — originality of the approach; not just a dashboard of the dataset.
- **Validity** — scientifically sound, technically feasible, honest about limitations.
- **Relevance** — actually responds to the chosen challenge; uses NASA (or partner agency) data in a meaningful, named way.
- **Presentation** — clear, compelling, well-communicated; the demo video and project page.

Space Apps specifics worth remembering: judges read the project page first, then the video, then the code. Global judging happens weeks after the event, so the hosted link must still work. Naming the exact datasets and endpoints used counts heavily for Relevance.

## Generic corporate / university hackathon
- **Technical difficulty** — how hard was this to build; what actually works.
- **Design / UX** — is it usable by the stated audience without the team explaining it.
- **Completeness** — is it a demo of a slice, or a working loop end to end.
- **Business or social value** — would anyone use or pay for this.
- **Pitch** — hook, problem, demo, ask; within the time limit.

## Sponsor-track events (API or cloud sponsor prizes)
- Depth of integration with the sponsor's product, not breadth.
- Visible use of the sponsor's tool in the demo.
- A clear statement in the write-up of what the sponsor product enabled that would otherwise be hard.

## Red flags judges notice fast
- "Future work" longer than "what works".
- Mock data presented as live.
- A demo that needs a local install with no hosted alternative.
- A video over three minutes, or a first 30 seconds with no product on screen.
